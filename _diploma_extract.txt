Обоснован выбор архитектуры SPA с отдельным REST API на Node.js (Express). Реализована система регистрации и аутентификации на основе bcrypt и JWT. Разработаны модули онлайн-бронирования столика, оформления заказа доставки или самовывоза, напоминания и отправки отзывов после визита. Реализован обратный отсчёт до начала и окончания бизнес-ланча с учётом часового пояса Europe/Minsk (понедельник–пятница, 12:00–16:00). Выполнено наполнение каталога из восьми категорий (48 позиций меню) скриптами schema.sql и seed_dishes.sql. Проведено тестирование основных пользовательских сценариев и сборка production-версии клиента для размещения на GitHub Pages.
Выводы: результатом дипломной работы стала разработка полностью функционирующего веб-приложения для ресторана «Прованс», реализующего основные сценарии взаимодействия гостя с заведением: просмотр меню, заказ доставки, бронирование, обратная связь. Применённый стек React — Express — PostgreSQL обеспечивает разделение ответственности между уровнями представления, бизнес-логики и данных, удобство сопровождения и возможность дальнейшего развития (административная панель, платёжные системы, уведомления).

ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ
В настоящей дипломной работе применяют следующие термины с соответствующими определениями.
API (Application Programming Interface) — программный интерфейс приложения; набор правил и инструментов, позволяющих клиентской и серверной частям обмениваться данными в формате запросов и ответов.
SPA (Single Page Application) — одностраничное приложение; веб-приложение, при котором основная логика отображения интерфейса выполняется в браузере без полной перезагрузки HTML-документа при переходах между разделами.
REST API — стиль архитектуры веб-сервисов, основанный на принципах передачи состояния представления (Representational State Transfer), в котором ресурсы доступны через стандартные HTTP-методы (GET, POST, PUT, PATCH, DELETE).
JWT (JSON Web Token) — открытый стандарт для передачи данных между сторонами в виде JSON-объекта, подписанного цифровой подписью; широко используется для реализации аутентификации без хранения сессий на сервере.
CORS (Cross-Origin Resource Sharing) — механизм браузера и сервера, разрешающий или запрещающий выполнение HTTP-запросов к API с другого источника (домена, порта или протокола).
ORM (Object-Relational Mapping) — технология программирования, связывающая реляционную базу данных с объектной моделью языка программирования; в данном проекте прямой доступ к PostgreSQL реализован через библиотеку pg без ORM.
PostgreSQL — объектно-реляционная система управления базами данных с открытым исходным кодом, поддерживающая транзакции, внешние ключи, тип JSONB и расширенные средства индексирования.
React — JavaScript-библиотека для построения пользовательских интерфейсов на основе компонентной модели и декларативного описания состояния.
TypeScript — строго типизированный язык программирования, основанный на JavaScript и добавляющий систему статических типов, что позволяет выявлять ошибки на этапе компиляции.
Create React App (CRA) — инструмент начальной настройки React-проекта, включающий сборку (webpack), dev-сервер, поддержку TypeScript и проксирование API-запросов в режиме разработки.
Express — минималистичный фреймворк для Node.js, предназначенный для создания HTTP-серверов и REST API.
Middleware — промежуточное программное обеспечение; функции, выполняемые между получением HTTP-запроса и отправкой ответа (аутентификация, логирование, обработка ошибок).
JSONB — бинарный тип данных PostgreSQL для хранения структурированных JSON-документов с возможностью индексирования и эффективного поиска по полям.
Хук (Hook) — специальная функция в React, позволяющая использовать состояние и побочные эффекты в функциональных компонентах.
Прокси (proxy) — перенаправление HTTP-запросов с dev-сервера фронтенда на backend-сервер в режиме разработки, что устраняет ограничения CORS при обращении к /api/*.

1 Теоретические основы разработки веб-приложений для ресторанного бизнеса
Первая глава дипломной работы формирует теоретическую базу для проектирования и реализации программного комплекса ресторана «Прованс». Рассматриваются особенности цифровизации сегмента HoReCa (Hotel / Restaurant / Café), сравнительный анализ существующих классов решений, архитектурные модели современных веб-приложений, программный стек и вопросы информационной безопасности при работе с персональными данными гостей.
1.1 Анализ существующих решений в сфере ресторанных веб-сервисов
Предприятия общественного питания в XXI веке конкурируют не только качеством кухни и сервиса в зале, но и удобством цифровых каналов. По данным отраслевых обзоров (в том числе за период пандемийных ограничений), доля заказов «на вынос» и доставки существенно выросла; даже после нормализации офлайн-посещений гости сохранили привычку предварительно изучать меню, фотографии интерьера и отзывы в интернете. Для ресторана это означает необходимость единой цифровой точки контакта — сайта или приложения, где совмещаются имидж, актуальное меню, бронирование и заказ без звонка.
Цифровизация в ресторанном бизнесе охватывает несколько уровней:
маркетинговый — привлечение аудитории, демонстрация концепции (итальянская кухня, авторские блюда, винная карта);
операционный — приём заявок на бронирование, фиксация заказов доставки, снижение нагрузки на телефонную линию;
аналитический — накопление данных о гостях (при регистрации), повторные визиты, обратная связь через отзывы;
сервисный — информирование о специальных предложениях (бизнес-ланч, события, дегустации).
Разрабатываемое приложение для «Прованс» ориентировано преимущественно на маркетинговый и операционный уровни в рамках учебного проекта, с заделом на аналитику через сохранённые заказы и бронирования.

Корпоративные сайты ресторанов ориентированы на имидж, информирование о концепции кухни, демонстрацию интерьера и контактных данных. Типичная структура включает главную страницу с визуальным акцентом (hero-блок), раздел «Меню» (часто в виде PDF или статической вёрстки), галерею фотографий, блок контактов и карту проезда. Продвинутые сайты добавляют онлайн-бронирование (форма с выбором даты, времени и числа гостей) и ссылку на доставку через внешний сервис.
Недостаток многих статических сайтов — отсутствие связной базы данных: при изменении цены или состава блюда требуется правка вёрстки или публикация нового PDF; заявки на бронь и заказы часто обрабатываются вручную (телефон, Instagram, Viber). Это увеличивает риск ошибок и не позволяет автоматически связать визит гостя с последующим отзывом.
Агрегаторы доставки (сервисы доставки еды в Республике Беларусь и на региональных рынках) предоставляют каталог множества заведений, корзину, оплату и отслеживание курьера. Для ресторана участие в агрегаторе расширяет охват, но сопровождается комиссией, унификацией карточки заведения и зависимостью от правил площадки (модерация меню, сроки доставки). Собственный модуль доставки на сайте ресторана сохраняет контроль над меню, ценами в BYN и оформлением заказа, а также позволяет накапливать прямую клиентскую базу (email, телефон, история заказов).
Сервисы бронирования столиков (OpenTable, Resy, локальные виджеты) специализируются на загрузке зала. Типичный функционал: проверка свободных слотов, подтверждение, SMS/email-напоминания. Для «Прованс» целесообразно встроить упрощённый сценарий (заявка без сложной схемы залов) в собственное приложение: гость остаётся в экосистеме бренда и может после визита получить запрос на отзыв в привязке к booking_id.
Конструкторы и CMS (Tilda, WordPress, Wix) ускоряют запуск landing page, но ограничивают реализацию нестандартного UX: анимированный прелоадер с послойным написанием логотипа, морфинг при скролле, динамический каталог из PostgreSQL, разделение dev/prod API. Кастомная разработка на React и Express оправдана, когда требуется точное соответствие фирменному стилю и несколько интегрированных подсистем в одном репозитории.

1.4 Архитектурные подходы к разработке веб-приложений
Выбор архитектуры определяет структуру кода, масштабируемость, безопасность и удобство сопровождения. Для ресторанного приложения с выраженным клиентским UX и компактным API рассмотрены три базовые модели.
Многостраничное приложение (MPA, Multi-Page Application) — классическая схема, при которой сервер (PHP, Django, JSP, шаблоны Node) генерирует полный HTML-документ на каждый URL. Преимущества: естественная индексация поисковыми роботами, быстрый First Contentful Paint для текстового контента, простота кэширования статики. Недостатки: полная перезагрузка при переходах, сложность реализации «богатых» интерфейсов (корзина с мгновенным пересчётом, вложенные модальные окна, сложная анимация логотипа) без дублирования логики на сервере и в браузере.
Одностраничное приложение (SPA, Single Page Application) — сервер отдаёт минимальный index.html и JavaScript-бандл; дальнейшая навигация выполняется клиентским маршрутизатором (react-router-dom в проекте). Состояние (корзина, токен авторизации, открытые модалки) хранится в памяти браузера. Преимущества: плавные переходы, единый контекст приложения (AuthProvider), богатые анимации (прелоадер Provans, морфинг hero-логотипа). Недостатки: больший объём начальной загрузки JS; SEO требует дополнительных мер (prerender, meta-теги через react-helmet, или миграция на SSR-фреймворк).
Гибридные фреймворки (Next.js, Remix, Nuxt) комбинируют SSR, SSG и клиентский рендеринг на уровне маршрутов. Они предпочтительны для контентных порталов с жёсткими SEO-требованиями. Для дипломного проекта «Прованс» выбрана связка CRA (SPA) + отдельный Express API как более прозрачная для демонстрации разделения ответственности на защите.

1.5 Трёхзвенная архитектура и REST
Классическая трёхзвенная архитектура (three-tier) разделяет систему на:
Уровень представления — браузер, React-компоненты, CSS.
Уровень бизнес-логики — Express, маршруты, middleware, валидация.
Уровень данных — PostgreSQL, SQL-запросы через пул pg.
Такое разделение соответствует принципу разделения ответственности (Separation of Concerns): изменение цены блюда в БД не требует пересборки клиента; изменение вёрстки карточки блюда не затрагивает схему таблиц. Взаимодействие клиента и сервера построено в стиле REST (Representational State Transfer): ресурсы (dishes, bookings, delivery-orders, auth) доступны по URL и HTTP-методам. Состояние приложения на сервере не хранится между запросами (stateless), что упрощает масштабирование; аутентификация вынесена в самодостаточный JWT, передаваемый клиентом в каждом защищённом запросе.

1.6 Клиент-серверное взаимодействие и CORS
В режиме разработки Create React App проксирует запросы /api/* на http://localhost:5000 (настройка "proxy" в package.json). Это устраняет CORS (Cross-Origin Resource Sharing) — механизм безопасности браузера, запрещающий по умолчанию запросы с localhost:3000 на localhost:5000 как с разных origin.
В production клиент и API могут располагаться на одном домене (reverse proxy nginx) или на разных — тогда на Express включается cors() и задаётся REACT_APP_API_URL. Критично не подставлять PUBLIC_URL (префикс /restaurant-app для статики GitHub Pages) в baseURL axios для API: иначе запрос уходит на /restaurant-app/api/dishes, прокси перенаправляет его на backend, а Express не имеет такого маршрута — каталог не загружается. В проекте модуль api.ts в development возвращает пустой baseURL, в production — явный origin API.
В React состояние распределено по уровням:
локальное — useState в формах бронирования, корзине, модальных окнах;
общее для поддерева — AuthContext (пользователь, токен, методы login/register/logout);
серверное как источник истины — каталог блюд загружается с API и кэшируется в состоянии DeliveryMenu до следующего запроса.
Для таймера бизнес-ланча применён useSyncExternalStore с общим планировщиком: подписывается только компонент BusinessLunchLine, а не вся главная страница с тяжёлой scroll-анимацией. Это соответствует рекомендациям React по минимизации каскадных перерисовок.
1.7Слой данных и JSONB
Сервер использует пул соединений pg (db.js): повторное использование TCP-соединений к PostgreSQL снижает накладные расходы при серии запросов. Каталог блюд — SQL с LEFT JOIN dish_categories; при ошибке схемы — запасной DISHES_MINIMAL_SQL.
Заказы доставки хранят items в JSONB — бинарный JSON PostgreSQL с индексацией. Теоретически альтернатива — нормализованные таблицы order_items (order_id, dish_id, quantity, price_snapshot); JSONB выбран для учебной простоты и фиксации произвольного состава корзины одним INSERT. Цена и название в момент заказа уже находятся в JSON клиента — историческая достоверность заказа сохраняется даже при удалении блюда из каталога.
2. Технологии и инструменты разработки
Выбор технологического стека — компромисс между требованиями проекта, квалификацией разработчика, экосистемой библиотек и перспективой сопровождения. Ниже обоснован состав стека «Прованс» и сравнение с альтернативами.
2.1 JavaScript как единый язык fullstack
Node.js — среда выполнения JavaScript вне браузера на движке V8. Использование одного языка на клиенте и сервере снижает когнитивную нагрузку: типы данных (JSON), асинхронность (Promise, async/await), инструменты npm общие для client/ и server/. Модель событийного цикла (event loop) Node эффективна для I/O-нагруженных веб-API (ожидание ответа БД, сеть), что соответствует профилю нагрузки ресторанного сайта (краткие запросы, без тяжёлых вычислений).
2.2 Клиентская платформа
React — библиотека для построения UI на основе компонентов — изолированных функций или классов, возвращающих разметку. Ключевые идеи:
декларативность — описание «как должно выглядеть» при данном state, а не пошаговая манипуляция DOM;
однонаправленный поток данных — props сверху вниз, события снизу вверх;
виртуальный DOM — сравнение деревьев и минимальные изменения реального DOM.
В проекте используется React 19 с функциональными компонентами и хуками (useState, useEffect, useCallback, useSyncExternalStore, memo). TypeScript добавляет статическую типизацию интерфейсов Dish, CartItem, props компонентов — ошибки несоответствия полей API и UI выявляются при компиляции.
Create React App (react-scripts 5) инкапсулирует Webpack, Babel, dev-сервер с hot reload, production-минификацию. Прокси "http://localhost:5000" решает проблему CORS в dev. Альтернатива — Vite (быстрее cold start); CRA выбран как стандарт учебных материалов и стабильная документация.
react-router-dom 6 реализует маршруты /, /gallery, /events/:slug без перезагрузки страницы. Параметр basename согласован с PUBLIC_URL.
axios — HTTP-клиент с перехватчиками и настройкой baseURL. Предпочтен встроенному fetch за удобство обработки ошибок и единообразие JSON.
Стилизация — кастомный CSS (App.css) без CSS-in-JS или Tailwind: полный контроль над фирменной палитрой (кремовый фон, золотистые акценты) и анимациями scroll/morph, что важно для премиального позиционирования ресторана.
2.3 Серверная платформа
Express 5 — минималистичный фреймворк поверх Node HTTP-модуля. Предоставляет:
маршрутизацию по префиксам (app.use('/api/auth', router));
цепочку middleware (cors, express.json(), authMiddleware);
централизованную обработку ошибок (расширяемо).
Альтернативы — Fastify (выше производительность), NestJS (структура для крупных команд). Express достаточен для дипломного API и хорошо документирован.
dotenv загружает секреты из .env (не коммитится в Git). bcryptjs хэширует пароли с солью (cost 10). jsonwebtoken формирует и проверяет JWT.

3 Системы аутентификации и управления пользователями
Идентификация и аутентификация пользователей — обязательный элемент современных веб-сервисов, работающих с персональными данными и историей операций. В ресторанном приложении учётная запись связывает разрозненные действия гостя (бронирование, доставка, отзыв) в единый профиль и позволяет реализовать сценарии «после визита» без повторного ввода контактов.
3.1 Авторизация
В информационной безопасности принято различать три этапа доступа:
идентификация — заявление личности («я — пользователь с email …»);
аутентификация — проверка заявления (пароль, токен, биометрия);
авторизация — решение, какие операции разрешены данному субъекту.
В проекте «Прованс» роль гостя единственна: после успешной аутентификации JWT даёт доступ только к собственным записям (user_id в запросах к БД). Отдельной роли администратора в текущей версии нет — это упрощение учебной модели, в промышленной системе потребовались бы разграничение прав (RBAC) и админ-панель.
Сессии на сервере (session-based). После входа сервер создаёт запись сессии (часто в Redis) и выдаёт клиенту cookie с идентификатором сессии. Плюсы: простой отзыв доступа (удаление сессии), сервер полностью контролирует состояние. Минусы: необходимость общего хранилища при нескольких экземплярах API, привязка к cookie и CSRF-защите.
Токены (token-based), в том числе JWT. Сервер подписывает payload (например, userId, срок действия) секретом JWT_SECRET; клиент хранит токен и отправляет в заголовке Authorization: Bearer …. Плюсы: stateless API, удобство для SPA и мобильных клиентов. Минусы: сложнее немедленно инвалидировать токен до истечения TTL; утечка токена из localStorage даёт доступ злоумышленнику (риск XSS).
OAuth 2.0 / OpenID Connect. Делегирование входа через Google, Facebook и т.д. Снижает барьер регистрации, но усложняет инфраструктуру. В дипломном проекте не применяется; в работе-аналоге (торговая площадка) используется NextAuth.
Для «Прованс» выбрана схема email + пароль + JWT, как баланс прозрачности реализации и достаточности для учебных целей.
3.2 Регистрация и хранение учётных данных
При регистрации (POST /api/auth/register) выполняется:
валидация обязательных полей (name, email, password, phone);
проверка уникальности email в таблице users;
хэширование пароля алгоритмом bcrypt (cost factor 10) — одностороннее преобразование с солью, устойчивое к перебору по радужным таблицам при утечке БД;
сохранение только password_hash, никогда открытого пароля;
выпуск JWT и возврат клиенту вместе с данными профиля.
Требования к паролю в учебной версии минимальны (длина на усмотрение клиента); в промышленной эксплуатации целесообразны политики сложности и проверка на утёкшие пароли (Have I Been Pwned API).
Персональные данные (ФИО, email, телефон) относятся к категории, подпадающей под законодательство о защите персональных данных (в РБ — Закон «О защите персональных данных»). Разработчик обязан обеспечить ограничение доступа к БД, HTTPS при передаче по сети и не публиковать .env с секретами.
3.3 JWT: структура и жизненный цикл
JWT состоит из трёх частей в Base64: заголовок (алгоритм подписи), payload (claims), подпись. В проекте в payload передаётся userId; срок действия — 7 суток (expiresIn: '7d').
Клиентский контекст AuthProvider (React):
при монтировании читает токен из localStorage;
при успешном login/register записывает токен и вызывает GET /api/auth/me;
при logout удаляет токен и сбрасывает состояние;
axios-перехватчик добавляет заголовок Authorization ко всем защищённым запросам.
Серверный middleware/auth.js:
извлекает Bearer-токен;
верифицирует подпись и срок;
устанавливает req.userId или возвращает 401 Unauthorized.
Принцип fail closed: при любой ошибке токена защищённый маршрут не выполняется «как для гостя», а отклоняется.

CORS: middleware cors на Express разрешает запросы с origin клиента. В development CRA-прокси направляет /api на localhost:5000, обходя cross-origin для браузера.
3.6 Связь учётной записи с бизнес-процессами ресторана
Учётная запись — не самоцель, а связка сценариев:
бронирование — запись в bookings с опциональным user_id; статус pending до подтверждения администратором (вне приложения);
отзыв — после визита (date/time в прошлом, reviewed = false) endpoint /api/reviews/pending предлагает оценку; после отправки или skip флаг reviewed блокирует повторные напоминания;
доставка — delivery_orders с JSONB-составом и привязкой к user_id для истории в модальном окне «Аккаунт».
Так формируется цифровой след гостя: от первого бронирования или регистрации до повторных заказов и обратной связи, что в перспективе поддерживает CRM и программы лояльности.
3.6.1 Нефункциональные требования и качество веб-приложений
Нефункциональные требования (НФТ) описывают, как система должна работать, а не что она делает. Их соблюдение определяет пригодность сайта ресторана для реальной эксплуатации и удовлетворённость гостей.
3.6.2Производительность и отзывчивость интерфейса
Гость ожидает быстрой загрузки главной страницы и плавной прокрутки. Факторы, влияющие на SPA:
размер бандла JavaScript (code splitting, lazy routes — в перспективе);
изображения — фотографии интерьера и блюд; в проекте применяется loading="lazy" для снижения начальной нагрузки;
частота перерисовки React — таймер бизнес-ланча вынесен в useSyncExternalStore и отдельный memo-компонент, чтобы секундный tick не перерисовывал всё дерево App (проблема «подвисания» при разработке была устранена именно этим).
Серверная часть для каталога из ~50 блюд укладывается в один SQL-запрос с JOIN; время ответа при локальной БД — миллисекунды. При росте меню целесообразны индексы и кэширование GET /api/dishes.
3.6.3Доступность (usability) и адаптивность
Интерфейс должен быть понятен без инструкции: явные кнопки «Забронировать», «Доставка», контакты в подвале. Адаптивная вёрстка (медиазапросы в CSS) обеспечивает чтение меню и оформление заказа с мобильного телефона — основной канал для доставки и бронирования «на ходу».
Требования WCAG (контраст, фокус клавиатуры, alt у изображений) в учебной версии выполнены частично; для production-аудита рекомендуется формальная проверка доступности.
3.6.4Надёжность и отказоустойчивость
База данных — единая точка отказа; резервное копирование pg_dump, мониторинг диска.
API — при ошибке подключения к PostgreSQL каталог не загружается; клиент показывает сообщение об ошибке. Запасной SQL (DISHES_MINIMAL_SQL) при отсутствии таблиц категорий повышает устойчивость при неполном развёртывании схемы.
Конфигурация — пароль БД приводится к строке в db.js (устранение ошибки SCRAM client password must be a string).
3.6.5 Масштабируемость и сопровождаемость
Текущая архитектура client + server + PostgreSQL вертикально масштабируется (больше CPU/RAM на одном VPS). Горизонтально: несколько инстансов Express за балансировщиком при общем секрете JWT и общей БД; sticky sessions не нужны из-за stateless JWT.
Сопровождаемость обеспечивается разделением на маршруты (routes/), единым api.ts на клиенте, SQL-скриптами версионирования меню. Отсутствие админ-UI компенсируется прозрачностью seed_dishes.sql для разработчика.
3.7 Локализация и предметная специфика
Контент и UI — на русском языке; цены в белорусских рублях; таймер бизнес-ланча учитывает часовой пояс Europe/Minsk и рабочие дни Пн–Пт, интервал 12:00–16:00 — отражение локального расписания ресторана в Гомеле, а не универсального UTC.

4.2 Проектирование базы данных
Логическая модель данных построена в PostgreSQL и описана в server/schema.sql. Начальное наполнение меню — в server/seed_dishes.sql (48 позиций в 8 категориях после актуализации ассортимента).
Сущность «Пользователь» (users). Хранит id, name, email (уникальный), phone, password_hash, created_at. Связана с бронированиями, отзывами и заказами доставки.
Сущность «Бронирование» (bookings). Поля: date, time, guests, контактные name, phone, опциональный user_id, status (по умолчанию pending), флаг reviewed. Внешний ключ на users с ON DELETE SET NULL — при удалении пользователя заявка сохраняется анонимно.
Сущность «Отзыв» (reviews). Связь с booking_id и user_id, оценка rating (CHECK 1–5), необязательный text. После создания отзыва у бронирования устанавливается reviewed = TRUE.
Сущность «Категория блюда» (dish_categories). name, sort_order — определяет порядок разделов в каталоге (пицца, паста и ризотто, супы, салаты, закуски, горячие блюда, гарниры, десерты).
Сущность «Блюдо» (dishes). Ссылка на категорию, name, description, price (DECIMAL), image_url, is_available. Цены соответствуют меню ресторана в белорусских рублях.
Сущность «Заказ доставки» (delivery_orders). Уникальный order_number (формат DEL-&lt;timestamp&gt;), user_id, состав items типа JSONB, total_amount, delivery_type (delivery / pickup), адрес, контакты, payment_method (online / cash), флаги is_paid, status, created_at. Хранение позиций в JSONB фиксирует состав заказа на момент оформления независимо от последующих изменений каталога.

5.2 Реализация базы данных и слоя доступа к данным
Развёртывание: выполнить schema.sql (создание таблиц и начальные данные) или применить seed_dishes.sql к существующей БД (скрипт очищает dishes и dish_categories, затем вставляет актуальное меню).
Модуль db.js формирует конфигурацию пула: при наличии DATABASE_URL используется строка подключения, иначе — отдельные поля; пароль приводится к строке String(process.env.PGPASSWORD ?? process.env.DB_PASSWORD ?? ''), что устраняет ошибку SCRAM «client password must be a string».
Пример фрагмента выдачи каталога (упрощённо):
SELECT d.id, d.name, d.description, d.price, d.category_id, d.image_url,
       dc.name AS category_name, dc.sort_order AS category_sort_order
FROM dishes d
LEFT JOIN dish_categories dc ON dc.id = d.category_id
WHERE COALESCE(d.is_available, true) = true
ORDER BY category_sort_order, d.id;
Заказ доставки сохраняется параметризованным запросом: items сериализуется в JSON (JSON.stringify(items)), что предотвращает SQL-инъекции.
5.3 Реализация системы аутентификации
Сервер. routes/auth.js: при регистрации проверяется уникальность email, пароль хэшируется bcrypt.hash(password, 10), возвращаются { token, user }. При входе — bcrypt.compare, при успехе — JWT с полезной нагрузкой { userId }, срок 7 дней.
Middleware (middleware/auth.js):
const token = req.headers.authorization?.split(' ')[1];
req.userId = jwt.verify(token, process.env.JWT_SECRET).userId;
Клиент. AuthProvider сохраняет токен в localStorage, при монтировании запрашивает /api/auth/me; при ошибке — очистка токена. Методы login, register, logout обновляют состояние и хранилище.

5.4 Реализация каталога, доставки и оформления заказа

5.5 Реализация бронирования и отзывов
Бронирование. Форма в App.tsx отправляет POST /api/bookings с полями date, time, guests, name, phone. Если пользователь авторизован, заголовок Authorization передаётся — сервер извлекает userId из JWT и записывает в user_id. Гостю показывается сообщение об успехе, форма закрывается по таймеру.

const jwt = require('jsonwebtoken');
module.exports = (req, res, next) =&gt; {
    const token = req.headers.authorization?.split(' ')[1];
    if (!token) return res.status(401).json({ error: 'Не авторизован' });
    try {
        req.userId = jwt.verify(token, process.env.JWT_SECRET).userId;
        next();
    } catch {
        res.status(401).json({ error: 'Недействительный токен' });
    }
};

router.post('/register', async (req, res) =&gt; {
    const { name, email, phone, password } = req.body;
    const existing = await pool.query('SELECT id FROM users WHERE email = $1', [email]);
    if (existing.rows.length &gt; 0)
        return res.status(400).json({ error: 'Email уже зарегистрирован' });
    const passwordHash = await bcrypt.hash(password, 10);
    const result = await pool.query(
        'INSERT INTO users (name, email, phone, password_hash) VALUES ($1, $2, $3, $4) RETURNING id, name, email, phone',
        [name, email, phone || null, passwordHash]
    );
    const user = result.rows[0];
    const token = jwt.sign({ userId: user.id }, process.env.JWT_SECRET, { expiresIn: '7d' });
    res.json({ token, user });
});

Фрагмент схемы базы данных (server/schema.sql)
CREATE TABLE dish_categories (
    id SERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    sort_order INT DEFAULT 0
);
CREATE TABLE dishes (
    id SERIAL PRIMARY KEY,
    category_id INT REFERENCES dish_categories(id),
    name VARCHAR(200) NOT NULL,
    description TEXT,
    price DECIMAL(10,2) NOT NULL,
    image_url VARCHAR(500),
    is_available BOOLEAN DEFAULT true
);
CREATE TABLE delivery_orders (
    id SERIAL PRIMARY KEY,
    user_id INT REFERENCES users(id),
    order_number VARCHAR(50) UNIQUE NOT NULL,
    items JSONB NOT NULL,
    total_amount DECIMAL(10,2) NOT NULL,
    delivery_type VARCHAR(20) NOT NULL,
    delivery_address TEXT,
    customer_name VARCHAR(200) NOT NULL,
    customer_phone VARCHAR(20) NOT NULL,
    payment_method VARCHAR(20) NOT NULL,
    is_paid BOOLEAN DEFAULT false,
    status VARCHAR(50) DEFAULT 'new',
    created_at TIMESTAMP DEFAULT NOW()
);
